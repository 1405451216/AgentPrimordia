### 2.2 协议式微内核评估

- **设计面**：`capability_agent.go` ~60 个 `With*`/`Get*` 链式方法 + `capabilities.go:77-83`「让能力成为接口而非配置字段」+ `react_capabilities.go:20-49` 类型断言发现 + `capCache`（react_loop.go:137-181 一次性解析）。评价：**设计自洽、向后兼容性好**——ReActConfig 字段与 Capable 接口并存，`capCache` 避免每轮类型断言（性能注释明确）。这是本仓库设计质量最高的部分之一。
- **代价**：能力注入路径有三条（直接字段/`CapabilityAgent.wrapSelf` 链式/`capCache` 断言），`chain_api.go` 的 `wrapSelf` 包装会产生包装器对象，新增能力需同时改 3-4 处（接口、CapabilityAgent、ReActAgent 断言、config/options），维护成本随能力数线性上升——当前 ~60 方法已是体量上限的信号。
- **循环依赖规避的副作用**：`capabilities.go:50-52` 因避免 import audit 包而定义了**第三份 AuditEvent 模型**（见 §六.2），同类模式（memory_readback 的 MemoryQuerier 可选接口）是刻意的接口拆分，可接受。

## 三、并发安全

> 口径：以下竞态均为**静态审查发现**（读代码推断的潜在数据竞争），CI Linux `-race` 常态化运行未报（本机 Windows 无 gcc 无法本地复现），**不得断言已实际发生**。触发与否取决于调用时序。

### 3.1 疑似竞态清单

**① pool dispatcher 三处（最高优先级）**

| 位置 | 问题 | 读写方 |
|------|------|--------|
| `internal/pool/dispatcher.go:499` | `pt.result = &TaskResult{...}` **无锁写** | 写：executeTask 执行 goroutine（:499-506）；读：`GetTask`/`ListTasks`/`GetTasksBySession` 在 `p.mu.RLock()` 下读 `pt.result`（dispatcher_ops.go:94-98,129-135）→ 同一字段既有裸写又有锁读，race detector 可捕获 |
| `internal/pool/dispatcher.go:549` | `model := p.model` **无锁读** | 读：createAgentForTask（:549，仅 factory 读取持 RLock，:543-545）；写：`SetModel` 持 `p.mu.Lock`（dispatcher_ops.go:215-218）→ 运行中换模型与建任务并发即竞态 |
| `internal/pool/dispatcher.go:594-638` | `acquireSlot` 超时绕过 + 唤醒不对称 | ① 定时器（`timerC`）**不触发 Cond 唤醒**——等待者在超时后仍阻塞，直到其他任务 releaseSlot Signal 才醒；超时只在 Wait 返回后顺带检查（:628-633）；② 最终 `select { case <-timerC: return ErrTimeout }` 非确定性：槽位已释放且定时器恰好在同一时刻到期时可能误报超时；③ ctx.Done 广播 goroutine 每等待者一个（可接受，done channel 保证不泄漏），但超时路径没有等效广播 |

**② agent stats 无锁写**：`react_loop_engine.go:76-81` `a.stats.StartTime/RequestID/Status` 直接写（无 statsMu），而 `react_lifecycle.go:26-36` `Stats()` 在 `statsMu.RLock` 下读同一结构；对照 `react_lifecycle.go:155-158`（ResumeFromCheckpoint 路径）对同样字段**正确地加锁**——同一文件内两套写法，engine 路径漏锁。`PlanRecoveries`/`ProcessCorrections` 等 v3.6 计数器在 `react_plan_executor.go:87-89`、`react_loop_tools.go:154-156` 均正确持 statsMu。

**③ SQLiteStore Close 后空指针**：`internal/memory/sqlite.go:149-162` `Close()` 持锁置 `s.db = nil`；但 `Stats`（:166-169）、`Search`（sqlite_search.go:61）、`SearchAdvanced`（:182）、`GetImportant`（:347）、`GetTimeline`（:369）、`GetMemoriesBySession`（:427）等**全部无锁直接读 `s.db`** → 关闭后调用即 nil 解引用 panic；关闭与读并发则为指针字段数据竞争。仅 `CleanupExpired`（:520-521）与 `Close` 加锁——读写锁使用极不均衡。

**④ 包级全局 embedding 缓存**：`internal/llm/cache.go:104` `var embeddingCache sync.Map`（全局，非实例级）+ `embeddingCacheMaxEntries=256`（:101）+ `putCachedEmbedding`（:133-145）超限时 `Range` 全量遍历删 1/4 —— O(n) 伪 LRU；`embeddingCacheSize`（:148-155）同样 O(n) Range。并发正确（sync.Map），但多个 store 实例共享同一全局缓存、淘汰无 TTL、O(n) 遍历在 256 上限下实际可忽略——属设计取舍而非正确性缺陷。

### 3.2 正面机制（并发安全做得好的部分）

- **状态原子化**：`poolTask.status` 走 `atomic.Value`（dispatcher.go:167-179 `loadStatus/storeStatus`）；pool 计数 `failedCount/completedCount/droppedEvents/dynamicConcurrency` 全 atomic（:125-140）；agent `atomicTurn` 热路径无锁（react_lifecycle.go:18-19）。
- **panic 收敛三处**：runLoop 内 tool 并行 goroutine recover（react_loop_tools.go:78-87）；executor 三层 recover（executor.go:180 safeExecute、:226、:267 批量）；A2A gRPC `RecoveryInterceptor`/`StreamRecoveryInterceptor`（a2a/interceptors.go:100-129，panic→Internal 错误）。
- **流式背压不泄漏**：`openai_provider.go:262-292` 限时发送+超时丢块+连续丢弃上限放弃整个流，goroutine 必然退出（defer close(ch) + 所有 return 路径终止）。
- **锁层级规整**：CorrelationStore 双层锁（map 锁 + record 锁，observability.go:123-177）；dispatcher 用 `semaMu`/`semaCond` 独立于 `p.mu` 避免锁嵌套；`emitEvent` 非阻塞+背压丢弃计数（dispatcher_ops.go:42-52）。
- **CI race 常态化**：ci.yml Linux/macOS `-race` 全量测试 + nightly `go test -race -count=1 ./...`（根 workspace 模式），是本仓库并发正确性的主要外部防线。

## 四、错误处理与公共 API

### 4.1 错误体系碎片化（本报告最高扣分项之一）

**① pkg.CodeError 是「无 Code() 的死路」**：`pkg/errors.go:19-22` `CodeError{Code, Message}` 只有 `Error()`，**没有 `Code() string` 方法**；而 `GetErrorCode`（:239-251）先做 `errors.As(err, &coded)`（`type coded interface{ Code() string }`）——**该分支永远不命中任何 CodeError**，`WithCode()` 构造的结构化错误码经 `GetErrorCode` 只能落回 sentinel 映射或返回 `"UNKNOWN"`。死代码路径真实存在。

**② 双套错误系统**：`internal/llm/config.go:100-177` 因「pkg 已依赖 llm，反向引用成环」另起 `ErrorCode`/`CodeError`/`WithCode`/`GetCodeFromError`（注释明言原因）。两个 `CodeError` 同名不同类型；llm 的 `GetCodeFromError` 用直接类型断言 `err.(*CodeError)`（:170-175），**对 `%w` 包装过的错误同样失效**。pkg 的 `GetErrorCode` 与 llm 的 `GetCodeFromError` 并存，调用方需要知道该用哪个。

**③ guardrail 拦截绕开 sentinel**：`react_loop_core.go:270` 输出端拦截返回 `fmt.Errorf("output blocked by guardrail")`（同一 return 内构造两次），而 `pkg.ErrOutputBlocked` 定义为 `errors.New("ap: output blocked by guardrail")`（errors.go:133）——**消息文本不同，errors.Is 永不匹配** → 护栏拦截错误经 `GetErrorCode` 返回 "UNKNOWN"、`IsAccessDenied` 漏判。输入端护栏（react_loop_engine.go:23-27）走 `pkg.ErrInputBlocked`（agent 定义），行为正确，形成对照。

**④ 悬空 sentinel**：`ErrPoolFull`（errors.go:77）与 `ErrContextCanceled`（:84）全仓 grep **无任何生产抛出点**（仅测试与文档引用）——作为 Stable 公共 API 承诺存在的错误，实际不可达。

**⑤ 最佳实践标杆**：`internal/llm/errors.go` `RetryableError`（Unwrap + `IsRetryable` + `CountsAsFailure` + Retry-After 解析 `ParseRetryAfter`/`RetryAfterFromHeaders` + `AsRetryableError` 提取）是**全仓设计最好的错误类型**：既携带语义（可重试/是否计熔断）又正确解包。pkg 层错误体系应向它看齐。

### 4.2 公共 API 门面（做得好的部分）

- `pkg/` = 纯 re-export 门面：48 个文件，53 处 `Stability:` 标注（23 Stable / 22 Experimental / 6 混合），类型别名 + var 构造器重赋值，无业务逻辑（仅少量辅助构造器，符合 AGENTS.md §4.2）。
- 三重机器门禁：`stability_compliance_test.go`（Stable 清单↔实际导出双向比对）、`deprecation_residual_test.go`（Removed-in-v4.0 API 不得再导出）、`version_gate_test.go`（版本一致性）；外加 api-contract 漂移门（Step 0 实测通过）。**这套「机器可证」机制是仓库可信度的核心资产。**

### 5.2 功能与语义问题

- **Search 双入口契约漂移**：`sqlite_search.go:23-66` `Search` 只遵守 `SessionID/RoleFilter/Limit/Offset`，**忽略 `MinScore/Tags`**；`SearchAdvanced`（:71-132）遵守 `MinScore/SemanticWeight/UseSemantic`。同一后端两种搜索语义，调用方换 API 即换行为——文档无差异说明。
- **租户隔离是过滤器级**：`tenant.go` 包注释自述「底层存储不做物理隔离…隔离通过 Search/Get 过滤实现」；`TenantScoped.Add` 仅在 Metadata 缺 tenant_id 时注入（:53 注释「如果缺失」）——**调用方可传任意 `Metadata["tenant_id"]` 伪造归属**；`Inner()` 明文「慎用：绕过租户隔离」。对「强隔离」宣称要打折扣（对等实现是物理分库/加密，见包内建议）。
- **FTS5 一致性是正面的**：`sqlite.go:117-136` `episodes_fts` external-content 表 + 三个触发器（INSERT/DELETE/UPDATE 双向同步），实现正确。
- **两套 MCP server 栈**：`internal/mcp/`（server.go + http_server.go，http_server 每请求 new Server）与 `internal/tools/mcp/`（完整 client/server/adapter/registry/prompts/resources/notifications 12 文件）。前者功能是后者的子集且零生产消费方（§2.3 孤儿包）——应删 `internal/mcp/` 或并入 tools/mcp。
- **resource_limiter 惰性实现**：`resource_limiter.go:51-82` `Acquire` 超限**直接返回 `ErrResourceExceeded`，从不等待**（`cond` 字段存在但 Acquire 未使用）；`memoryMB` 字段从不跟踪（ResourceMemory 落 default 分支直接拒绝）；`:104` `var _ = time.Second` 未用 import hack；`ErrResourceTimeout`（:11）为死代码（Acquire 永不超时等待）。对照 `pool.acquireSlot` 的 Cond 实现，tools 层明显是占位。
- **FailureStore 不持久**：`persist/failure.go:89-146` 仅 `MemoryFailureStore`（map + RWMutex），无任何持久化变体；包名叫 persist、放 persist/ 下却丢失进程重启数据。「失败重放」能力在 Go 侧的实际持久性依赖 `ReplayFailure` 内嵌的 checkpoint（react_failure.go:64），FailureStore 本身是内存态。
- **正面：executor 纵深防御链**（`executor.go`）：ScopePolicy 权限检查（:126-131）→ RequireConfirmation 确认（:139-149，无回调默认拒绝）→ 每工具超时（:172-177）→ panic recover 三层（:180/:226/:267）→ 敏感参数脱敏 `redactSensitiveArgs`（:384-409，16 类敏感 key 正则，日志截断 256 字符）。builtin 工具纵深防御：filesystem 根约束+符号链接逃逸检查、shell 命令白名单+元字符拒绝（`security.ContainsShellMetacharacter` 委托链）、web/api SSRF 默认关闭、code_execution 显式 opt-in。**这是全仓安全质量最高的部分。**
- **CP-first 领导者选举**：`persist/leader_election.go` 头注释「网络分区下宁可停止写入也不冒脑裂风险（CP 优先于 AP）」，心跳续约+降级模式+健康让位，仅依赖 Coordinator 接口（memory/fs/etcd/redis 可插拔）——设计正确。

### 9.2 总体判断

AgentPrimordia 处于「**从可信走向可证**」的完成阶段：v3.3→v4.0 的实证路线不是口号——35 项声称 33 项有代码证据、`TestAPIContractNoDrift` 漂移门实跑通过、版本四方一致、CI 供应链闭环，**「声称完成」的可信度较 v2.0 时代（git tag 仅 v0.7.0、STATUS 3/8 阶段不实）有质的提升**。核心引擎（ReActLoop + 微内核 + 记忆/规划/自愈）是全仓最成熟的部分，安全纵深是行业级水准。

**最突出的风险排序**：
1. **并发正确性隐患**（pool 竞态 ×3 + sqlite Close + stats 漏锁）——目前依赖 CI -race 兜底，一旦在高并发/关闭时序下触发，表现是偶发数据竞争与 nil panic，难排查；
2. **错误体系统一性**（双套 CodeError、guardrail 绕 sentinel、死路 errors.As）——公共 API 承诺的结构化错误码实际不可达，破坏「可编程错误处理」契约；
3. **孤儿代码沉淀**（6 包 + react/ 骨架 + studio stub + workflow 垫片）——体量不大但持续增加认知税；
4. **文档/发布产物陈旧**（nightly 必失败、Helm/Terraform 过期、LICENSE 矛盾、examples 死链）——拉低工程形象且 terraform 路径实际不可用；
5. **双线对齐缺口**（TS 静默跳过 4 套件）——spec 增长未驱动实现，跨语言承诺逐步稀释。
