## 3. 根因分析

### 3.1 实现成熟度不足

v7.1-rc1 定位为**接口骨架 + 基础算法**（rc1），非生产级实现：

- `LifecycleCreator` 返回占位工件，不生成可执行工具
- `IntelligenceHook.OnTurnEnd` 创建工具后丢弃，不回注 agent 工具注册表
- 规划器增加 LLM 调用开销但不产生有效决策增益
- 多模态 bench 的 B 臂原生输入未带来信息增益（sensenova 文本模式已足够处理）

### 3.2 Bench 设计缺陷（已修复）

首轮实验发现 3 个 bench 运行器 bug，修复后重跑：

| 问题 | 修复 | 效果 |
|------|------|------|
| gap bench: `writeGapTool()` 注册通用 Shell 而非命名工具 | 创建 `shellCommandTool` 实现 `tools.Tool` 接口 | B 臂 -15.3pp → -11.9pp |
| intelligence bench: 纯模拟，不创建 Agent | 重写为真实 Agent + `registeringCreator` | 架构修复，数字不变 |
| live bench: B 臂 MaxTurns=20 + 噪声提示 | 统一 MaxTurns=15，移除 `analyzeTask()` | B 臂 -6.8pp → **-1.7pp** |

### 3.3 根本矛盾

B 臂的框架能力（缺口检测、工具创建、规划、世界模型）在**当前任务难度**下无法体现价值：

- 多数任务可用 shell + filesystem 直接完成（awk/sed/grep）
- B 臂的额外 Hook 调用消耗 token 预算和轮次
- 专用工具虽已注册，LLM 倾向使用熟悉的 shell 而非新工具

## 4. 结论与建议

### 结论

v7.1-rc1 的框架骨架已正确搭建：
- 接口定义完整（6 个新包，29 个接口/类型）
- Hook 桥接链路通畅（IntelligenceHook → HookManager → ReAct 循环）
- 工具注册链路通畅（creator → registeringCreator → Registry → agent 可用）
- 全量编译通过，单测全绿

但实现成熟度不足以产生统计显著的验收增益。所有 McNemar p > 0.05。

### 建议

1. **验收达标推至 v7.2**：需要生产级实现（非 stub）
2. **优先深化 gap 和 intelligence**：这两个方向的 B 臂有最大提升空间
3. **重新设计 bench 任务**：增加必须使用专用工具才能完成的硬任务
4. **增大 agent 预算**：给 B 臂更多轮次/token 以发挥框架能力
