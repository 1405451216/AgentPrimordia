# v7.1 框架迭代设计规格

> **版本**: v7.1.0-draft
> **日期**: 2026-09-05
> **状态**: 设计评审通过，待实施规划

---

## 1. 概述

v7.1 是 v7.0.0 GA 之后的第一个迭代版本，采用**五命题并行验收**策略：

1. **V7 验证收尾**：完成 E-1/E-4/E-5 的形式化 A/B 验收
2. **多模态 Agent**：图像/音频/视频输入输出能力
3. **规划能力增强**：生产级子目标分解 + 动态重规划 + 失败恢复
4. **可观测性升级**：统一 trace → 指标 → 审计全链路
5. **工具智能统一**：整合 tool_learning + tools/lifecycle 为统一入口

每个新能力方向均需完整验收数字（McNemar 精确检验或确定性断言），不走降级豁免。

## 3. 命题 2：多模态 Agent

### 3.1 目标

让 Agent 能原生处理图像/音频/视频输入，输出多模态内容，对接多模态 LLM Provider。

### 3.2 架构

```
internal/agent/multimodal/
├── types.go        — MultimodalMessage（Text + Image + Audio + Video 内容块）
├── codec.go        — 编解码器（base64/URL/文件路径 → 统一 ContentPart）
├── provider.go     — 多模态 Provider 接口（VisionRequest/AudioRequest/VideoRequest）
├── adapter.go      — 现有 LLM Provider 的多模态适配（OpenAI GPT-4o, Qwen-VL 等）
├── tools.go        — 多模态内置工具（image_describe, audio_transcribe, image_generate）
└── hooks.go        — ReAct 循环的多模态 Hook（消息预处理/响应后处理）
```

### 3.3 关键设计决策

- **扩展而非替换**：`MultimodalMessage` 扩展 `Message`，纯文本路径零影响
- **向后兼容**：不支持多模态的 Provider 自动降级为文本-only
- **工具注册**：多模态内置工具走 `tools/lifecycle/` 注册路径（为工具智能统一铺路）

### 3.4 验收实验

- **题面**：20 道多模态任务（10 视觉 QA + 5 音频转写 + 5 图文混合推理）
- **A 臂**：纯文本描述（图像转 OCR 文本后输入）
- **B 臂**：原生多模态（图像/音频直接输入）
- **判定**：确定性断言（答案匹配/关键词包含）
- **样本量**：McNemar +20pp, ω=0.30 → n=59/arm = 118 次运行
- **达成门**：McNemar p<0.05 且配对差值 ≥ +20pp

## 4. 命题 3：规划能力增强

### 4.1 目标

将 `internal/agent/planning/` 从实验状态升级为生产级规划器，提升长程任务成功率。

### 4.2 架构

```
internal/agent/planning/
├── planner.go        — Planner 接口 + 生产实现（升级现有 ToT/MCTS）
├── decomposer.go     — 子目标分解器（大目标 → 有序子目标 DAG）
├── replanner.go      — 动态重规划（执行偏离计划时触发重分解）
├── recovery.go       — 规划失败恢复（死路检测 + 回退 + 替代路径搜索）
├── approval.go       — 人机协作审批（高风险动作暂停等待人类确认）
├── plan_state.go     — 计划状态机（pending→active→blocked→completed/failed）
└── hooks.go          — ReAct 循环的规划 Hook（计划生成/执行/校验）
```

### 4.3 关键设计决策

- **子目标 DAG** 而非线性计划——支持并行子目标和条件分支
- **重规划触发**：观察与预期偏差 > 阈值、子目标失败、预算消耗过快
- **审批门** 走 `governance/` 策略引擎——可配置哪些动作类型需要审批
- **与世界模型协同**：planner 消费 worldmodel 的状态图做前瞻预演

### 4.4 验收实验

- **题面**：复用 `docs/evals/long-horizon-v1.json`（24 题）
- **A 臂**：当前 ReAct 默认策略（无规划器）
- **B 臂**：ReAct + 增强规划器（子目标分解 + 重规划 + 失败恢复）
- **判定**：沙箱终态确定性断言
- **样本量**：108 配对 = 216 运行（复用 v6.1 设计）
- **达成门**：McNemar p<0.05 且配对差值 ≥ +15pp

## 5. 命题 4：可观测性升级

### 5.1 目标

统一 `observability/` 和 `otel/`，构建全链路可观测体系。

### 5.2 架构

```
internal/observability/
├── pipeline.go       — 统一管线（trace span → 指标聚合 → 审计事件关联）
├── trace.go          — Trace 层：Agent 每轮 ReAct 生成 span
├── metrics.go        — 指标层：Prometheus 导出
├── audit_link.go     — 审计关联层：trace_id ↔ audit_event_id 双向映射
├── dashboard.go      — 实时仪表盘后端（HTTP API）
├── alert.go          — 异常告警（规则引擎）
├── export/
│   ├── otlp.go       — OTLP 导出（兼容 Jaeger/Prometheus/Grafana）
│   └── log.go        — 日志导出（结构化 JSON）
└── hooks.go          — ReAct 循环的观测 Hook
```

### 5.3 关键设计决策

- **合并 otel/ 进 observability/**：otel 作为 OTLP 导出子包
- **trace_id 贯穿全链路**：Agent 启动时生成，所有下游携带同一 trace_id
- **告警规则** 走 `governance/` 策略引擎
- **仪表盘** 纯 HTTP API（JSON），前端由 Studio 消费

### 5.4 验收标准（确定性断言，不走 McNemar）

| 断言 | 描述 |
|------|------|
| A1 | 任意 Agent 运行后，trace 链路完整覆盖所有 ReAct 轮次和工具调用 |
| A2 | trace_id 可正向查询到所有关联审计事件 |
| A3 | 告警规则触发后 < 5s 发出通知 |
| A4 | 指标导出兼容 Prometheus scrape 格式 |
| A5 | 仪表盘 API 返回实时数据延迟 < 1s |

## 6. 命题 5：工具智能统一

### 6.1 目标

整合 `tool_learning/`（参数调优）和 `tools/lifecycle/`（工具创建），构建统一工具智能系统。

### 6.2 架构

```
internal/tools/intelligence/
├── intelligence.go                — ToolIntelligence 统一入口
├── create/
│   ├── detector.go                — 缺口检测（从失败轨迹识别 missing_tool 模式）
│   └── creator.go                 — 工具生成（复用 lifecycle autoloop）
├── optimize/
│   ├── profiler.go                — 工具性能画像（per-tool 统计）
│   ├── tuner.go                   — 参数调优器（升级 tool_learning）
│   └── selector.go                — 工具选择优化（学习最优选择策略）
├── reuse/
│   ├── catalog.go                 — 工具目录（索引 + 能力描述）
│   └── matcher.go                 — 任务-工具匹配
├── audit.go                       — 全链路审计
└── hooks.go                       — ReAct 循环 Hook
```

### 6.3 关键设计决策

- **三阶段统一**：detect → create/optimize → reuse
- **优化器** 基于性能画像做数据驱动调优
- **工具目录** 支持跨 Agent 共享——与 federation skill-card 协议对齐
- **向后兼容**：原 `tool_learning/` 和 `tools/lifecycle/` 公共 API 保留为 thin wrapper

### 6.4 验收实验

- **题面**：30 道工具密集型任务
- **A 臂**：当前分离系统（lifecycle + tool_learning，无统一入口）
- **B 臂**：统一工具智能（intelligence 入口）
- **判定**：任务成功率 + 工具复用率
- **样本量**：McNemar +20pp, ω=0.30 → n=59/arm = 118 次运行
- **达成门**：McNemar p<0.05 且配对差值 ≥ +20pp（成功率）；工具复用率 B 臂 ≥ 2× A 臂

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| API 算力不足 | 验收实验无法跑完 | 分优先级：V7收尾 > 工具智能 > 规划增强 > 多模态 |
| 接口对齐失败 | 跨线集成返工 | 第 1 周强制接口评审，变更需通知依赖方 |
| 多模态 Provider 不可用 | 多模态实验无法起算 | 备选：sensenova 多模态端点或本地 mock |
| 规划器引入额外延迟 | 轮次预算超标 | 规划器设独立预算，不占 ReAct 主循环额度 |

## 9. 约束

- 所有新模块仅使用 Go 标准库（白名单外依赖需审批）
- TDD 强制：先写测试再写实现
- 中文注释
- 安全边界不变：宿主零写入零加载（INV-0）
- 统计口径：McNemar 精确检验 α=0.05 双侧，Wilson 95% 区间
